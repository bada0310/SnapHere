# 커밋 · 브랜치 규칙 (명세 연결용)

`docs/git-strategy.md`의 Conventional Commits 규칙을 그대로 쓰되, **어느 요구사항과 어느 API를 구현했는지 커밋에서 바로 보이게** 한다.
리뷰어가 명세서를 열지 않고도 "이 커밋이 명세의 어디를 덮는가"를 알 수 있어야 하고, 나중에 `git log --grep=PST-016` 으로 요구사항을 역추적할 수 있어야 한다.

---

## 1. 브랜치 이름

```text
<type>/<scope>-<description>
```

기존 규칙 그대로다. 여기에 **요구사항 ID 범위를 description에 넣는다.**

```text
feature/backend-post-pst013-015
└──┬──┘ └──┬──┘ └─┬─┘ └───┬────┘
  type   scope  기능    요구사항 ID 범위
```

| 예시 | 의미 |
| --- | --- |
| `feature/backend-post` | 게시글 도메인 통합 브랜치 (골격) |
| `feature/backend-post-pst013-015` | 이미지 업로드 URL 발급 (`PST-013`~`PST-015`) |
| `feature/backend-post-pst022-028` | 위치 신뢰등급 판정 (`PST-022`~`PST-028`) |
| `fix/backend-post-pst030` | 장소별 게시글 한도 버그 수정 (`PST-030`) |

**중첩 경로를 쓰지 않는다.** `feature/backend-post/pst013` 처럼 만들면 git이 `feature/backend-post` 브랜치를 동시에 가질 수 없다. 슬래시 대신 하이픈으로 잇는다.

ID가 연속이 아니면 대표 범위만 쓰고 정확한 목록은 커밋 메시지에 적는다 — 브랜치 이름이 길어지면 아무도 못 친다.

---

## 2. 커밋 메시지 양식

```text
<type>(<scope>): <기능 명세서의 기능 이름>

기능 명세  : <페이지> > <하위 페이지> > <세부 기능>
요구사항 ID: <쉼표로 나열>
API ID     : <쉼표로 나열 · 없으면 '해당 없음'>

- <변경 사항 1>
- <변경 사항 2>
- <변경 사항 3>
```

### 제목

- **기능 명세서 `3. 기능 명세서` 시트의 "세부 기능" 이름을 그대로 쓴다.** 새로 지어내지 않는다.
- 명세서에 없는 작업(빌드 설정, 리팩터링 등)이면 기능 이름 대신 무엇을 했는지 쓰고, 본문의 `기능 명세` 줄에 `해당 없음`이라고 적는다.
- 50자 안쪽, 마침표 없음.

### 머리 3줄

| 줄 | 내용 | 비울 수 있나 |
| --- | --- | --- |
| `기능 명세` | `3. 기능 명세서`의 위치. `2.3 사진·캡션·태그 > 업로드 실행` 형식 | 명세 밖 작업이면 `해당 없음` |
| `요구사항 ID` | 이 커밋이 실제로 구현·수정한 ID만. 참고만 한 ID는 넣지 않는다 | 비울 수 없음 |
| `API ID` | 구현한 엔드포인트의 API ID. 배치는 `JOB-013` 형식 | 엔드포인트가 없으면 `해당 없음` |

### 본문 목록

- 한 줄에 하나의 변경. 파일 목록이 아니라 **무엇이 달라졌는지**를 쓴다.
- 검증 규칙·제한값처럼 숫자가 있는 것은 숫자를 적는다 (`하루 30개 초과 시 429`).
- 요구사항 ID를 줄 안에 다시 써도 된다. 여러 요구사항을 한 커밋에 담았을 때 어느 줄이 어느 ID인지 보여주려면 그게 낫다.

### 예시

```text
feat(backend): 이미지 업로드 URL 발급

기능 명세  : 2.3 사진·캡션·태그 > 업로드 실행
요구사항 ID: PST-013, PST-014, PST-015, USER-004, SYS-020
API ID     : API-PST-001

- POST /api/v1/media/presigned-urls 추가. 게시글 1~4개, 프로필 1개 (PST-013)
- 허용 형식 jpeg·png·heic·webp, 장당 10MB 초과 시 MEDIA_TOO_LARGE 413 (PST-015)
- 서명 주소 유효 시간 5분 고정 (SYS-020)
- 프로필 이미지도 같은 흐름을 쓰도록 purpose 파라미터 분리 (USER-004)
```

```text
fix(backend): 장소별 게시글 한도

기능 명세  : 2.3 사진·캡션·태그 > 한도 초과 안내
요구사항 ID: PST-030
API ID     : API-PST-003

- 같은 장소 하루 3개 판정 기준일을 UTC에서 Asia/Seoul 자정으로 수정 (SYS-005)
- 초과 시 POST_PLACE_DAILY_LIMIT 429 + retryAfterSec 반환
```

```text
chore(backend): Spring Boot 프로젝트 초기 구성

기능 명세  : 해당 없음
요구사항 ID: SYS-001, SYS-002, SYS-003, SYS-004, SYS-016
API ID     : 해당 없음

- Gradle Kotlin DSL + Java 21 + Spring Boot 3.5.6 골격 추가
- 공통 응답 봉투 ApiResponse 추가 (SYS-001)
- 에러 코드 체계 ErrorCode·ErrorBody·GlobalExceptionHandler 추가 (SYS-002)
```

## 3. 하지 말 것 (Negative Prompt)

AI에게 커밋 메시지를 맡길 때 이 블록을 그대로 붙여넣는다.

```text
아래는 커밋 메시지를 쓸 때 절대 하지 말아야 할 것이다.

- 요구사항 ID 줄을 비우지 마라. 구현한 ID가 정말 없으면 그 작업은 커밋을 나눠라.
- 존재하지 않는 요구사항 ID·API ID를 지어내지 마라. 명세서에 실재하는 ID만 쓰고,
  확실하지 않으면 "확인 필요"라고 적고 멈춰라.
- 참고만 한 ID를 구현한 것처럼 나열하지 마라. 이 커밋이 실제로 코드로 만든 것만 적어라.
- 제목을 지어내지 마라. 기능 명세서 "세부 기능" 이름을 그대로 가져와라.
- 제목에 "구현", "작업", "수정" 만 쓴 모호한 문장을 넣지 마라. 무엇을 만들었는지 적어라.
- 본문에 파일 목록을 나열하지 마라. git이 이미 보여준다. 동작이 어떻게 달라졌는지 적어라.
- 한 커밋에 여러 기능 명세 항목을 섞지 마라. 섞였으면 커밋을 나눠라.
- 요구사항 범위를 "PST 전체" 처럼 뭉뚱그리지 마라. 개별 ID를 나열하라.
- 숫자를 생략하지 마라. "한도 적용" 이 아니라 "하루 30개 초과 시 429" 로 적어라.
- 영어와 한국어를 한 문장 안에서 섞지 마라. 식별자·코드명은 원문 그대로 두고 설명은 한국어로 쓴다.
```

## 4. PR 본문

`.github/pull_request_template.md`의 **작업 내용** 항목에 커밋의 머리 3줄을 합쳐서 적는다.

```md
## 작업 내용

- 기능 명세: 2.3 사진·캡션·태그 > 업로드 실행
- 요구사항: PST-013, PST-014, PST-015, USER-004, SYS-020
- API: API-PST-001

이미지 업로드용 S3 Presigned URL 발급 엔드포인트를 추가했습니다.
```

PR 제목은 기존 규칙대로 `[<type>](<scope>): <subject>` 를 쓴다.

## 5. 게시글 도메인 분할 계획 (`PST-001`~`PST-049`)

49건을 한 PR에 담으면 리뷰가 불가능하다. `3. 기능 명세서`의 항목 단위로 6개로 나눈다.
**앞 브랜치에서 다음 브랜치를 딴다.** 뒤 작업이 앞 작업의 코드를 쓰기 때문이다. PR도 이 순서로 머지한다.

| # | 브랜치 | 기능 명세 | 요구사항 ID | API ID |
| --- | --- | --- | --- | --- |
| 0 | `feature/backend-post` | 해당 없음 (골격) | `SYS-001`~`SYS-004`, `SYS-016` | 해당 없음 |
| 1 | `feature/backend-post-pst013-015` | 2.3 사진·캡션·태그 > 업로드 실행 | `PST-013`, `PST-014`, `PST-015`, `USER-004`, `SYS-020` | `API-PST-001` |
| 2 | `feature/backend-post-pst022-028` | 2.2 위치 확인 > 등급 미리보기 | `PST-022`~`PST-028`, `PST-046`~`PST-049` | `API-PST-002` |
| 3 | `feature/backend-post-pst001-021` | 2.3 사진·캡션·태그 > 게시글 등록 | `PST-001`~`PST-012`, `PST-016`~`PST-021`, `PST-029`~`PST-032`, `VST-001`, `VST-002` | `API-PST-003` |
| 4 | `feature/backend-post-pst033-039` | 5.1 본문 · 5.5 관리 | `PST-033`~`PST-039`, `SOC-013`, `PLC-013` | `API-PST-004`~`API-PST-008` |
| 5 | `feature/backend-post-pst040-042` | 5.2 반응 > 좋아요 | `PST-040`, `PST-041`, `PST-042`, `CMU-023` | `API-PST-009`~`API-PST-012` |
| 6 | `feature/backend-post-pst043-045` | 5.5 관리 > 삭제·신고 | `PST-043`, `PST-044`, `PST-045` | `API-PST-013` |

`PST-007`(사진 위 텍스트·이모티콘)은 클라이언트 작업이라 백엔드 분할에 들어가지 않는다.

| --- | --- | --- |

1·2번은 DB 를 쓰지 않는 부분만 골라낸 것이다 — 업로드는 S3 서명만 만들고, 등급 미리보기는
좌표 거리만 계산한다. 3번부터는 실제 INSERT 가 필요해서 `chore/backend-database` 가 먼저 들어가야 한다.
그 브랜치는 요구사항을 구현하지 않으므로 요구사항 ID 를 브랜치 이름에 넣지 않고 `chore/` 로 둔다.

## 6. 코드 작성 시 하지 말 것 (Negative Prompt)

머지 충돌의 대부분은 로직이 아니라 **주석과 공용 파일**에서 난다.
AI에게 코드를 맡길 때 이 블록을 그대로 붙여넣는다.

```text
아래는 이 저장소에서 코드를 쓸 때 절대 하지 말아야 할 것이다.

[주석]
- 기능을 바꾸지 않은 파일의 기존 주석을 다시 쓰거나 형식만 고치지 마라.
  내용이 같은데 줄바꿈만 달라져도 그 줄 전체가 충돌 영역이 된다.
- 여러 사람이 함께 고치는 파일(ErrorCode.java, application.yml, README.md,
  설정 클래스)에는 긴 블록 주석을 넣지 마라. 한 줄로 끝내라.
- 설계 이유를 파일 안에 길게 적지 마라. 그건 커밋 메시지와 PR 본문에 적는다.
  코드 주석에는 "이 줄이 왜 이렇게 생겼는가"만 남긴다.
- 파일 상단이나 섹션 구분용 배너 주석을 공용 파일에 넣지 마라.
  그 줄 근처를 누가 건드리든 충돌한다.
- 주석을 코드에서 떨어뜨려 놓지 마라. 설명하는 코드 바로 위에 붙인다.

[공용 파일]
- ErrorCode enum 에 값을 추가할 때 기존 값의 순서나 줄바꿈을 건드리지 마라.
  본인 도메인 구역에만 추가한다.
- application.yml 에 항목을 넣을 때 다른 도메인 블록을 정렬하거나 옮기지 마라.
- import 문을 자동 정렬로 통째로 재배치하지 마라. 필요한 줄만 더한다.

[빌드 산출물 · 파일 삭제]
- 빌드 산출물이나 남의 파일을 임의로 지우지 마라.
  backend/build, backend/bin, .gradle, node_modules, 로컬 설정 파일 전부 해당된다.
  지워야 한다고 판단되면 무엇을 왜 지우는지 먼저 말하고 승인을 받아라.
- .gitignore 로 추적에서 빼는 것과 파일을 지우는 것은 다르다.
  git rm --cached 는 인덱스에서만 빼는 것이고 로컬 파일은 남는다. 그렇게 처리하라.
- 작업 중 생긴 임시 파일을 저장소 폴더에 남기지 마라.

[명세 문서]
- 명세서에서 행이나 항목을 지우지 마라. 변경과 추가만 한다.
  빼야 한다고 판단되면 먼저 말하고 승인을 받아라.
- 이미 기록된 과거 버전의 변경 이력을 고치거나 지우지 마라.
  잘못됐으면 새 버전에 정정 줄을 추가한다.
- 과거 버전을 서술한 문장("v1.1.3에서 분리했다")의 버전 번호를
  일괄 치환으로 올리지 마라. 그건 이력이다.

[브랜치]
- 재구성한 브랜치의 이전 PR을 열어 둔 채 방치하지 마라.
  낡은 상태가 머지되면 이미 지운 파일이 되살아난다.
  브랜치를 다시 만들었으면 이전 PR을 먼저 닫아라.
```

### 왜 주석이 충돌을 만드는가

git은 줄 단위로 병합한다. 두 사람이 **같은 줄 또는 가까운 줄**을 고치면 자동 병합을 포기한다.
긴 주석 블록은 그 "가까운 줄" 범위를 넓힌다 — 10줄짜리 javadoc이 붙어 있으면,
그 아래 메서드를 고친 사람과 주석을 다듬은 사람이 충돌한다.

기능이 겹치지 않는데도 충돌이 나는 경우는 대부분 이것이다.

### 구조적으로 충돌하는 파일

`common/error/ErrorCode.java` 는 모든 도메인이 같은 enum에 값을 추가한다.
enum은 마지막 값에 세미콜론이 붙어서 **누가 추가하든 그 줄을 건드린다.**
지금까지 충돌이 난 파일 중 가장 잦았다.

도메인별로 나누면(`PostErrorCode`, `AuthErrorCode` …) 사라지지만 팀원 코드도 함께 고쳐야 한다.
**논의 필요** 항목으로 남긴다.

## 7. 환경 버전 고정

팀원마다 다른 버전을 쓰면 "내 컴퓨터에선 되는데"가 생긴다. 아래 네 개는 고정이다.

| 항목 | 버전 |
| --- | --- |
| PostgreSQL | **Percona Distribution 17.10.2** |
| PostGIS | **3.6.2** |
| JDK | **21.0.11** |
| Gradle | **8.14** |

```bash
docker build -t snaphere/percona-postgresql-with-postgis:17.10.2-postgis3.6.2 \
  backend/docker/postgres
docker run -d --name snaphere-db -p 5432:5432 \
  -e POSTGRES_DB=snaphere -e POSTGRES_USER=snaphere -e POSTGRES_PASSWORD=snaphere \
  snaphere/percona-postgresql-with-postgis:17.10.2-postgis3.6.2
```

공식 Percona 17.10.2 이미지는 PostGIS 3.5.7까지만 제공하므로 저장소의 Dockerfile로
3.6.2를 빌드한다. PostGIS 소스와 Percona 기반 이미지 digest를 모두 고정해 재현성을 유지한다.

**분기에 한 번 팀이 함께 최신 패치로 올린다.** 못 박아 두고 영영 안 올리면
그 사이 고쳐진 보안·데이터 손상 수정을 그대로 안고 간다 — 오래된 마이너 버전을
쓰는 것이 마이너 업그레이드보다 더 위험하다.
